# M0：Windows 上的最小实验链

M0 只回答一个问题：这台机器是否有一条可复现、可观察、可重新接管的 MiniLinux 最小实验链？

```text
Windows PowerShell → Clang/LLD → x86_64 ELF → Limine BIOS CD
                   → QEMU TCG → kernel_main → COM1 串口/panic
                   → QEMU GDB stub → GDB 断点/寄存器/调用栈
```

在这台机器上，命令行 GitHub 直连曾 DNS 超时。以下下载示例只为该命令指定本地代理 `127.0.0.1:7897`，没有修改 Git 全局配置。代理地址需随实际网络环境替换；安装不依赖代理常驻。

```powershell
$tools = 'D:\DevTools\MiniLinux'
New-Item -ItemType Directory -Force -Path "$tools\downloads", "$tools\llvm-23.1.1", "$tools\limine-12.9.0" | Out-Null

curl.exe -x http://127.0.0.1:7897 -L --fail -o "$tools\downloads\clang-llvm-23.1.1-win64.tar.zst" 'https://github.com/llvm/llvm-project/releases/download/llvmorg-23.1.1/clang%2Bllvm-23.1.1-x86_64-pc-windows-msvc.tar.zst'
curl.exe -x http://127.0.0.1:7897 -L --fail -o "$tools\downloads\limine-binary-v12.9.0.zip" 'https://github.com/Limine-Bootloader/Limine/releases/download/v12.9.0/limine-binary.zip'
curl.exe -x http://127.0.0.1:7897 -L --fail -o "$tools\downloads\qemu-w64-setup-20260811.exe" 'https://qemu.weilnetz.de/w64/qemu-w64-setup-20260811.exe'

Get-FileHash -Algorithm SHA256 "$tools\downloads\clang-llvm-23.1.1-win64.tar.zst"
Get-FileHash -Algorithm SHA256 "$tools\downloads\limine-binary-v12.9.0.zip"
Get-FileHash -Algorithm SHA512 "$tools\downloads\qemu-w64-setup-20260811.exe"
```

核对上表后再解压和安装：

```powershell
tar.exe -xf "$tools\downloads\clang-llvm-23.1.1-win64.tar.zst" -C "$tools\llvm-23.1.1"
Expand-Archive -LiteralPath "$tools\downloads\limine-binary-v12.9.0.zip" -DestinationPath "$tools\limine-12.9.0"

$qemuDest = "$tools\qemu-20260811"
$installer = "$tools\downloads\qemu-w64-setup-20260811.exe"
$process = Start-Process -FilePath $installer -ArgumentList '/S',('/D='+$qemuDest) -WindowStyle Hidden -Wait -PassThru
if ($process.ExitCode -ne 0) { throw 'QEMU installation failed.' }

& 'D:\python-3.10.6\python.exe' -m pip install --target "$tools\python-packages" 'pycdlib==1.20.0'
```

本机现有 GDB 路径由 `tools/debug.ps1` 默认使用，换一台机器时可用 `-Gdb` 指定另一个支持 ELF x86_64 的 GDB。构建脚本也接受 `-ToolRoot`，其默认值是上表路径。

## 运行与证据

执行 `tools/m0.ps1` 会依次核对工具、构建 ELF、生成 ISO、用 Windows `tar` 独立提取并核对镜像内容、启动 QEMU、连接 GDB。也可以单独运行 `tools/build.ps1`、`tools/image.ps1`、`tools/verify-image.ps1`、`tools/run.ps1`、`tools/debug.ps1`。镜像输出到 `D:\DevTools\MiniLinux\images`，ELF 和本地诊断日志输出到源码目录的 `build/`；它们不会写入仓库跟踪内容。串口原始输出在 `build/serial.log`，GDB 原始输出在 `build/gdb-trace.log`。

实际观察：

```text
ELF64, x86-64, EXEC; entry 0xffffffff80001000
MiniLinux M0: entered kernel_main
MiniLinux PANIC: M0 reached its intentional stop
GDB breakpoint: kernel_main, RIP 0xffffffff80001004, CS 0x28
GDB breakpoint: panic, caller kernel_main
```

`CS & 3 == 0`，此处执行在内核特权级。panic 是 M0 的预期停止点：串口先给出可观察证据，随后内核执行 `hlt` 循环；运行脚本验收日志后关闭该 QEMU 进程。

`verify-image.ps1` 比较 ISO 内的 `kernel.elf`、`limine.conf`、`limine-bios.sys` 与本轮输入的 SHA256。它曾拒绝由另一份干净源码副本生成、但串口文本相同的旧 ISO：`ISO payload differs from this build: kernel.elf`。重新生成镜像后该门通过。这个反例说明，串口文本只能证明运行行为，不能单独证明运行的是本轮 ELF。

## 镜像坑与当前边界

最初用 pycdlib 写出的 ISO 只有 450560 字节，`kernel.elf` 的最后一个数据区紧贴镜像末端。SeaBIOS 已从 CD 启动，但 Limine 报 `iso9660: failed to read file data`，串口为空。查阅 Limine 的 `iso9660_read` 和 `volume_read` 路径后，在 ISO 末端追加 1 MiB 空白扇区；重新从未经 `bios-install` 修改的镜像启动，内核与 GDB 证据均出现。这里的解释是对源码和实验结果的推断，解决办法由启动实验证实。

这个镜像是 **BIOS El Torito CD**，仅在 QEMU 的 BIOS 启动路径上验收。Limine 官方 [hybrid ISO 流程](https://github.com/Limine-Bootloader/Limine/blob/v12.x/USAGE.md)使用 xorriso、UEFI 文件与 `bios-install`；本次没有验证 UEFI、真实硬件或 hybrid ISO。M0 的结论只覆盖上面的 Windows → QEMU 实验链。
