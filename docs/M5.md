# M5：文件里的字节怎样回到用户程序

前提是 M4 的真实用户入口、syscall 返回、抢占和局部故障恢复已经通过。现在加一个内存文件表与每个 task 自己的两个打开槽；每次打开产生独立偏移。提供 open/read/close，用户文件名用长度传递，不让内核无界扫描用户字符串。

RamFS 的内容就是固定名字、字节数组和长度。read 在文件长度内取字节，先完整检查用户输出区，再写入并推进偏移。读取 EOF 返回 0；不存在的名字、无效描述符、重复关闭、打开槽耗尽，以及越过用户页/写入只读代码页必须返回错误。拒绝的读取不得消费文件偏移，也不得先改写一半输出区。

用户程序分两次读出 `/hello.txt`，自己逐字节核对，并经串口写出。两次独立打开的首字节相同，各 task 也有独立偏移；读到末尾再读得 0。核心闭环为：用户程序→时钟/内存→受控入口→RamFS→字节返回→用户核对与输出。

这是只读、无磁盘的最小 RamFS；不宣称 VFS 框架、POSIX 描述符兼容或磁盘恢复。Shell 不参与证明。未知情况或字节/偏移不一致均失败，不以出现文件内容字符串代替用户程序的实际核对。

## 实际结果

`tools/stage.ps1 -Milestone M5` 在 64/256 MiB 和 GDB 中通过，见 [本轮运行](evidence/m5-pass.log)。两个 CPL3 程序各自打开文件、以 5+12 字节读取并核对，输出 `hello from ramfs`。每个 task 观察到三次成功打开、18 个返回字节（完整文件 17，加另一次独立打开的首字节）、至少两次 EOF 与四种描述符/文件错误，关闭后没有已用槽。

代码页输出与跨越未映射页的 read 均返回 -2；跨页调用前写入的八个哨兵字节保持不变，随后正常 read 仍得到文件开头。用户报告在真实 syscall 返回之后，故障和幸存者顺序沿用 M4；所有实验分配归还。本轮没有遇到新的红灯，不人为制造一份“首败”。
