# 薄用户态上层

本轮从 `747952c` 的 M0–M6 候选出发，先把人能操作的用户态入口做实，再接黑白前端。历史实验仍使用原来的构建入口。

## 边界与顺序

1. 新增 `LAB` 构建：PID 1/init 创建 shell，二者都在 CPL3。
2. shell 支持 `help`、`ls`、`cat`、`ps`、`run`。程序固定内嵌：hello、reader、counter-a、counter-b；可同时运行两个 counter。没有任意 ELF 加载、目录树、完整终端编辑或 POSIX。
3. 创建、等待、退出和故障停止形成最小生命周期；子程序退出后回收页表和用户页，槽位可以复用。
4. COM1 传递真实输入输出；COM2 输出独立的机制记录。观察窗展示实际 PID、CR3、映射、时钟切换和 syscall，不能从演示文字推断状态。
5. 宿主使用 Python 标准库桥接 QEMU 与浏览器；页面使用原生 HTML/CSS/JavaScript，无新增 npm 或 Python 包。内核和用户程序保持无第三方运行库。

前端沿用用户选定的黑白草图，收窄为本实现的字段。企鹅是视觉致敬；不引入图形内核或模拟 shell。

## 证明条件

- 通过串口输入完成 help、文件枚举、读取、进程观察和运行程序，未知命令/文件不破坏下一轮。
- 两个 counter 同时活跃，时钟确实切换，相同数据虚拟地址对应不同物理页，用户持续核对自己的标记。
- 子程序退出/故障后 shell 能接管；连续运行后可用页计数恢复。
- 浏览器操作到达同一真实客体，观察窗能关联 cat 的文件 syscall；重启清空上一客体状态，失联明确可见。
- 页面核心操作、较窄窗口、键盘输入与真实运行通过验证；M0–M6 与已有反例适量回归。

## 运行与读代码

```powershell
# 准备 LAB 的 ELF/ISO、校验载荷，然后启动宿主桥接与真实客体
.\tools\lab.ps1
# 打开 http://127.0.0.1:8080/
# 停止桥接后再执行自动验证
.\tools\check-lab.ps1
```

`lab.ps1 -MemoryMiB 256 -Port 8081` 可以改变两项实验参数。默认保持单核、64 MiB、8080。停止页面中的 guest 只停止客体，桥接仍允许 restart；停止运行脚本的 Ctrl+C 同时关闭桥接和自己创建的 QEMU。

读代码的顺序是 `user/laboratory.c:user_main` → shell 的普通分词循环 → `call` → `kernel/laboratory.c:syscall_dispatch`。spawn 给每个槽位分配私有页表、代码、数据与用户栈；wait 保存父进程现场，timer 选择下一个 ready 槽位；exit 切换地址空间以后回收退出程序的用户页和页表。等待过的槽位重新可用。用户 `mem` 能读回实际可用页数。

所有程序使用同一份内嵌代码，通过普通 switch 选择程序入口；每个实例拥有自己的物理页和 CR3。这不是从 RamFS 加载任意二进制。五个演示程序是 hello、reader、counter-a、counter-b、fault，分别展示用户态、文件系统调用、时钟/地址隔离和故障后的接管。

浏览器 → localhost HTTP → Python 标准库 → COM1 → shell 的 `input` syscall。COM2 是内核单独输出的制表符记录，Python 按行解析，页面只读取观察结果。单字符回显和空输入轮询不刷满 trace；有用事件保留最近 2000 条，终端保留最近 64000 字符。清空视图与暂停 trace 都不会改变客体执行。

## 已观察到的结果

- `help/ls/cat/ps/run` 都经过真实串口输入；不存在的文件、命令、程序，过长行和多余参数被拒绝，下一轮仍可操作。
- `check` 拒绝内核指针、只读目标、无效程序与 wait；拒绝 read 没有消费文件偏移。填满六个子槽位以后第七个创建返回失败，等待后槽位和页数恢复。
- 64/256 MiB 都连续运行 24 个 hello/reader，再运行两个 counter 和故障程序；返回 shell 后可用页数分别恢复为 15976/65116。这个数属于本轮固定镜像，不是系统容量合同。
- 两个 counter 不调用 yield，时钟真实双向切换；同一 `0x600000` 虚拟地址对应不同物理页，物理标记分别是 `0xa110` 与 `0xb220`，用户不断检查自己的标记。
- `run fault` 触发用户态 vector 14，退出状态 142；shell 能继续 `cat hello.txt`。回收后只剩 init 与 shell。
- 浏览器验证了 cat 到 open/read/close 的记录关联、选择 PID 和 syscall 参数、暂停/恢复、清空、停止/重启、键盘回忆命令与故障观察。页面显示最近记录的 CPL3 入口，不声称显示 CPU 此刻的特权级。
- M0–M6 完整回归、坏寄存器/数据别名拒绝和原有错题本都通过。共享 `user_range` 只抽取原有实现，仍检查各级页表权限；旧实验入口、ABI 编号及其停机点保留。

## 首败与修补

1. C 警告拒绝了未初始化的局部指针和输入字符。明确初始化后重新构建通过；没有降低 `-Werror`。
2. 用户代码的聚合零初始化让编译器生成了 `memset` 调用，freestanding 链接首次失败。将原有逐字节 helpers 单独编译到用户地址空间，仍无 libc；静态符号与运行库段检查通过。
3. 第一次历史全回归各阶段已经通过，但最终残留检查发现仍在运行的 LAB 预览 QEMU。这是实验设置冲突。先停止自己的预览，原残留守卫保持不变，串行重跑后通过；没有把活着的 QEMU 当成内核错误，也没有掩盖这个失败。
4. 视觉首轮有过多小框，后续字号放大、调度并入进程表、模式记录合并，手册不再固定高度截住全文。用户最终选定上下反转的 38.2:61.8 比例，并明确 PC 的问题是外框过长。复验发现长历史会撑高终端；限制上排外框为 520–640 px，在框内滚动，保留字号与舒适表格留白。移动端取消固定高度。
5. 用户实际查看又发现整页仍需要滚动，下排被截住，右上观察区与左下日志留有大片空白。旧限制只覆盖上排，1366×768 视口中整页仍高 1184 px；此前视觉通过没有证明“一窗完整外框”。重新分配桌面视口的剩余高度，观察区改为进程/内存并排、syscall 在下，日志的时间/事件/地址分列；重复信息收紧，完整地址和正文大小保留。六档桌面视口均无整页溢出，390/700 两档仍为纵向长页面；记录、手册框内滚动，切换手册主题返回开头。新截图与几何读回见 [视觉复验](../design-qa.md)。这次只调整网页，不重开已验证的内核边界。

## 运行范围

客体默认 64 MiB、一个 CPU。LAB 使用 `-accel tcg,tb-size=32` 明确限制翻译缓存；参数含义见 [QEMU 官方调用文档](https://www.qemu.org/docs/master/system/invocation.html)。Windows 本机一次运行的 QEMU 工作集采样为 66,723,840 字节，约 64 MiB；此前默认缓存下约 1.14 GiB。工作集采样不等于承诺的总内存上限，Python、浏览器和其他应用另计。该参数下两档用户态验证都已重跑通过。

init/shell 异常仍是明确 panic，不实现守护重生、孤儿进程收养、信号或 job control。shell 用非阻塞串口轮询，所以空闲时仍占用 CPU；停止客体能释放它，不能将它描述为低功耗 idle 实现。串口输入是 ASCII、每行最多 95 字符；只提供退格与宿主的上一条命令回忆，不是完整 TTY。

固定上限为八个进程槽位，代码最多十六页，用户栈两页。RamFS 仍只有两个只读文件。观察记录是实验数据，不是瞬时 CPU 探针；长期运行只保留近期窗口。HTTP 只监听 localhost，不提供远程控制、登录、网络协议栈或部署服务。
