# M6：什么时候可以把两个 task 称为 process

M5 已把用户程序→受控入口→文件字节→用户核对与输出串起来。M6 额外证明地址空间隔离：两个根页表各自映射代码、数据、用户栈；数据使用同一个虚拟地址 `0x600000`，物理页不同。每个程序写自己的标记并在时钟轮转后反复核对，同时增长自己的计数。内核经 HHDM 独立读回两页，核对两个根、两个物理页、两个标记和非零计数。

保留单核数组轮转。内核映射是两者共享的 supervisor 上半部；数据与用户栈可写且 NX，代码只读且可执行。内核栈仍是每个 task 的独立固定数组。没有 fork、COW、共享页、动态链接或 POSIX 兼容声明。

四次客体实验分别让一个程序在完成文件核对与报告后读取内核页、写只读代码页、执行 NX 数据页、读取未映射地址。每次必须核对指定 CR2、CPL3 与 #PF 错误码；另一个程序在故障之后继续计算、报告并退出。任意其他异常不是通过。

再用 GDB 故意把第二个空间的数据映射指向第一个的物理页。两个用户栈仍独立，用户标记检查应拒绝这份错误的“隔离”，不能依靠内核先做静态比较才发现。最后回到正常映像复验。只有这些事实与同机精确提交干净克隆成立，才升级 process 的声明；GitHub 发布状态仍另行记录。

## 当前本机观察

正常 M6 在 64/256 MiB 与 GDB 通过。256 MiB 轮中两个根为 `0x83000` / `0x8e000`，同一 VA 的数据物理页为 `0x89000` / `0x94000`，分别保留 `0xa110` / `0xa111`，计数均非零。具体地址由本轮内存图决定，不是代码的固定要求。

四种用户 #PF 分别得到：内核读取 error=5，代码写入 error=7，数据执行 error=21，未映射读取 error=4；均核对 CR2，故障之后幸存者继续，并在实验结束归还全部页。完整运行见 [M6 记录](evidence/m6-pass.log)。

首个别名反例 [没有注入成功](evidence/m6-alias-first-failure.log)：当前 MinGW GDB 自动选 Windows ABI，调用 freestanding SysV 目标函数时两个 API 都返回 false，正常链照常通过。这不是“隔离反例也通过”，而是无效的工具尝试。现在直接按四级索引定位第二个根的叶项，保留权限位、修改物理页并读回；[用户标记正确拒绝](evidence/m6-alias-rejected.log)。GDB 只用于观察与内存修改，不把此 Windows 构建宣传为可可靠调用目标 C 函数。正常映像随后重新运行通过；注入只修改该次客体内存。

目前仍是本机候选。精确提交的全部里程碑回归与干净克隆待最后闭环记录，不提前升级公开主线状态。
